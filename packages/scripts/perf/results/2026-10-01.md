# Performance campaign 2026-10-01

## 4. Capacity model (replaces's estimate)

Measured, one instance on this machine:

- **Planning figure: 50 mixed requests/s per web instance per core** (budgets met with p95 59 ms at 55 % CPU over
  10 min); it breaks at ~60/s.'s user model (1 000 concurrent members, one request per ~10 s ≈ 100/s)
  therefore needs **two instances on this hardware**, more on typical cloud vCPUs (see the memory point and the host
  table).
- **PostgreSQL is not the constraint at this scale**: ~690 TPS and ≤ 8 busy connections at 50/s, 100 % cache hits,
  35 % of a core. Stage 1's pooler is not needed for the first few instances: 10 connections per instance
  plus the worker fits the default `max_connections = 100` up to ~8 instances.
- **Memory per web instance:** ~1.5 GB RSS with the 1 GB heap cap; up to ~2.3 GB without it on this machine. The cap
  raises CPU per request by about half at 50/s, so with it plan on **~40 req/s per instance** here and **~25–35 on a
  cloud vCPU**; a larger cap (e.g. 1 536 MB) is likely cheaper but unmeasured.
- **First bottleneck under overload:** web CPU, which now sheds as 503, not database connections.
