# Failure Scenarios

### 2.1 Application restart (web): in-flight requests and graceful shutdown

| Failure                                               | Detection                                                                 | Expected behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Recovery                                                           | User impact                                                                                                                                                                                                                                            |
| ----------------------------------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Planned stop (deploy) or a `SIGTERM` from the runtime | `web.drain.started` log (`trigger: endpoint` or `SIGTERM`); readiness 503 | `POST /health/drain` (token-gated like health details) flips readiness to 503 while liveness stays 200, so the load balancer stops sending traffic; open message streams end and a draining instance refuses new ones (the browser reconnects to the live instance after `retry: 5000`). On `SIGTERM` Next.js stops accepting connections and finishes every request it is already serving, then exits; a `SIGTERM` listener drains too, for runtimes that signal without calling the endpoint | The other colour serves; this one exits well inside the 30 s grace | None for requests already being served. A request that reaches a draining instance without the drain step (a raw `SIGTERM` racing a reused keep-alive socket) can see a connection reset, which the proxy retries; this is why the deploy drains first |

Evidence: drill `packages/scripts/drills/web-shutdown.ts` (production build, real signed-in message stream, ten signed-in `/dashboard` requests slowed to 100 ms per database round trip through a fault proxy so they are mid-render when `SIGTERM` arrives); tests `apps/web/src/app/health/health-routes.test.ts`, `src/infrastructure/health/health-service.test.ts`, `src/app/api/v1/messages/stream/route.test.ts`.

**Drill record — 2026-10-01 — `10869f4` (branch `phase-14-reliability`, local compose stack):**

| Check                                      | Result | Detail                                                                |
| ------------------------------------------ | ------ | --------------------------------------------------------------------- |
| instance becomes ready                     | pass   | 200                                                                   |
| POST /health/drain accepted                | pass   | 202                                                                   |
| readiness 503, liveness 200 while draining | pass   | ready 503, live 200                                                   |
| open message stream ends on drain          | pass   | 50 ms after drain                                                     |
| in-flight requests complete after SIGTERM  | pass   | 10/10 answered 200 (/dashboard, slowest 13 960 ms, SIGTERM at 400 ms) |
| process exits within the 30 s grace        | pass   | 13 593 ms, code 143                                                   |
| no new connections after exit              | pass   | refused                                                               |

**Fixed:** readiness never drained (nothing called `startDraining()`, and Next.js closes its listener on `SIGTERM` before application handlers run, so the drain needs its own trigger); an open message stream never ended, which would hold the server's `close()` open until the grace period killed the process. The health service now lives on `globalThis` so `instrumentation.ts` and the routes share one instance (as the metrics registry does).

**Note:** ten concurrent signed-in `/dashboard` renders took up to 14 s at 100 ms per database round trip, i.e. a dashboard render makes many sequential round trips. Measured: at normal database latency `/dashboard` is p95 82 ms inside a 50 requests/s mixed load, so it was left as is.
