# R-7 — Disk full or filling

**Alerts:** `HostDiskFull` (page) · `HostDiskFilling`, `HostInodesLow`, `PgWalGrowing`, `NodeExporterDown` (ticket).

## What it means

- `HostDiskFilling` / `HostDiskFull`: a filesystem on the host is more than 80 % / 90 % full. At 100 % PostgreSQL stops accepting writes, and Redis's append-only file and the container logs stop too.
- `HostInodesLow`: more than 90 % of the inodes are used. Writes fail when they run out, however much space is free.
- `PgWalGrowing`: `pg_wal` holds more than 2 GiB and is still growing. PostgreSQL keeps every segment until it is archived, so this is almost always WAL archiving failing ([R-8](./R-8.md)).
- `NodeExporterDown`: no host metrics, so neither the disk alerts nor the backup-timestamp alerts can fire.

## Check first

1. `df -h` and `df -i` on the host: which filesystem?
2. What grew: `sudo du -xh --max-depth=2 /var/lib/docker | sort -h | tail`, then `docker system df -v`.
3. Release images: about 1 GB each. `deploy/deploy.sh status` lists the releases that are still needed for rollback.
4. Container logs: each service's json-file log is capped (compose.yml), but a service without the cap can grow without limit.
5. `pg_wal`: Grafana → Data, or `docker compose exec postgres du -sh /var/lib/postgresql/18/docker/pg_wal`. If `WalArchiveFailing` is firing too, fix archiving first.
6. `NodeExporterDown`: `deploy/monitoring.sh ps` and `deploy/monitoring.sh logs node-exporter`.

## Mitigate

- Delete images that no recent `releases.log` line names, as in the README's **Operating** section. **Never run `docker system prune -a`**: it deletes the rollback images.
- `docker builder prune` on a server that builds in build mode.
- WAL piling up → fix the archive command ([R-8](./R-8.md)). The segments are removed once archived. Never delete files from `pg_wal` by hand.
- Still short → grow the volume at the provider, then `resize2fs`.

## Escalate

PostgreSQL refusing writes (disk full) → SEV-1 (reliability §10.5).

## Resolved when

Every filesystem is below 80 % and `pg_wal` is back under 2 GiB, or shrinking.
