# R-8 — Backups, WAL archiving, restore tests

**Alerts:** `WalArchiveFailing`, `WalArchiveStale`, `RestoreTestOverdue` (page) · `BaseBackupMissed`, `BackupJobOverdue`, `BackupMetricsMissing` (ticket).

## What it means

Postgres hands every WAL segment to pgBackRest (`archive_command`), which pushes it, encrypted, to the off-host repository bucket (ADR-011). Base backups, the logical dump, the uploads mirror and the restore test run from cron through `deploy/backup.sh`, and each success updates `alumini_backup_last_success_timestamp_seconds{kind}`.

- **Archiving failing or stale:** point-in-time recovery stops at the last archived segment, so a host loss now loses everything since then. Postgres also keeps every unarchived segment in `pg_wal`, and **when the disk fills, Postgres stops**. This is the urgent case.
- **A base backup, verify, dump or uploads run is late:** no data is at risk yet; a restore takes longer or the second line of defence is stale.
- **Restore test overdue:** nobody knows whether the backups restore (SRS §46).

## Check first

All from `deploy/` on the server.

1. `./backup.sh info`: does the stanza report `status: ok`, and does the WAL range reach the present?
2. `docker compose logs --since 1h postgres | grep -i -E 'archive|pgbackrest'`: pgBackRest's error explains most failures (credentials, TLS, bucket name, network, `[103]` repository not reachable, `[044]` stanza mismatch).
3. `tail -20 backups.log`: which job failed, and when it last succeeded. `crontab -l`: is the job still scheduled?
4. Disk: `df -h` on the Docker volume path, and `docker compose exec postgres du -sh /var/lib/postgresql/18/docker/pg_wal`.
5. `BackupMetricsMissing` only: is node_exporter running with `--collector.textfile.directory=/var/lib/prometheus/node-exporter`, and are there `alumini_backup_*.prom` files in it?

## Mitigate

- **Repository unreachable or credentials rejected:** fix it at the provider or in `.env` (`BACKUP_S3_*`), then `docker compose up -d postgres` to reload the environment. Postgres retries archiving on its own, and the backlog drains. Confirm with `./backup.sh check`.
- **Disk filling with WAL and archiving not fixable within the hour:** add disk space. **Do not** delete files from `pg_wal`, and do not set `archive_command` to `true`. Either one throws away the segments that recovery needs, and the next full backup becomes the only recovery point. If it must happen to keep the site up, take a full backup (`./backup.sh backup full`) as soon as archiving works again and record the gap in the incident.
- **Base backup failed:** rerun it by hand (`./backup.sh backup diff`, or `full` if the last full is older than a week) and read the error.
- **Verify failed:** run it again. If it fails twice, the repository holds a damaged file. Take a new full backup now, keep the failing output, and open an incident: restores that need the damaged backup may fail.
- **Restore test failed or overdue:** run `./backup.sh restore-test` by hand and read which step failed: restore, recovery, migrations, constraints, or amcheck. A failure in the checks after a successful restore usually means a real data problem in production too; run `./backup.sh integrity` against `postgres` (it takes locks briefly, so run it off-peak).
- **Uploads mirror or dump late:** run `./backup.sh uploads` or `./backup.sh dump` by hand.

## Escalate

- Archiving has been broken for longer than the RPO (15 minutes of writes at risk) and the cause is not found → page the second operator. The restore runbook (reliability §7.3) may be needed if the host is also unhealthy.
- The repository is lost or its cipher passphrase is unavailable → this is an incident in its own right: start a new stanza in a new bucket (`./backup.sh init`) immediately, so that new backups exist again.

## Resolved when

`./backup.sh check` succeeds, `pg_stat_archiver_failed_count` stops increasing, and every `alumini_backup_last_success_timestamp_seconds{kind}` is inside its schedule (deploy/README.md step 8).
