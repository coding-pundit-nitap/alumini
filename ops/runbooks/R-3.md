# R-3 — Outbox stuck, worker down, queue backlog

**Alerts:** `WorkerDown`, `OutboxStuck` (page) · `OutboxEventsQuarantined`, `QueueBacklogGrowing` (ticket).

## What it means

Every change that triggers background work writes an outbox row in the same transaction. The worker's relay moves those rows to the queue Redis, and its processors run the jobs. Requests keep succeeding while this is broken; emails, notifications and other side effects are delayed, not lost.

- `WorkerDown`: the worker process is not answering scrapes.
- `OutboxStuck`: the oldest unpublished row is older than 5 minutes — the relay is not publishing.
- `OutboxEventsQuarantined`: the relay gave up on rows it could not publish.
- `QueueBacklogGrowing`: jobs are queued faster than they run.

## Check first

1. Is the worker running? `curl -s http://<worker>:3001/health/ready` shows `database`, `queueRedis`, `relay`, `draining`.
2. Is the queue Redis reachable and below its memory limit? (`QueueRedisDown`/`QueueRedisMemoryHigh` → [R-6](./R-6.md).)
3. Worker logs: `outbox.relay.poll_failed`, `outbox.event.quarantined`, `job.retry`, `job.dead`.
4. **Grafana → Async:** queue depth by state, job outcomes, p95 job duration per job.
5. Quarantined rows: `pnpm worker:cli outbox:failed`.

## Mitigate

- Worker down or wedged → restart it. In-flight jobs return to the queue.
- Queue Redis problem → [R-6](./R-6.md).
- Quarantined rows: fix the cause (usually a payload a new release cannot handle), then `pnpm worker:cli outbox:release --all` (or by id). **Never delete outbox rows.**
- Backlog with a healthy worker: find the slow job in "Job p95 duration"; a provider slowdown (email) → [R-11](./R-11.md).

## Escalate

Backlog still growing after a restart →.

## Resolved when

`outbox_oldest_unpublished_age_seconds` is back under a minute and waiting jobs are falling.
