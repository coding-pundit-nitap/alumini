# R-1 — Site down / readiness failing / monitoring silent

**Alerts:** `WebDown`, `ReadinessFailing`, `SiteProbeFailing` (page) · `Watchdog` stopped arriving at the dead-man's switch (page, from outside).

## What it means

- `WebDown`: Prometheus cannot scrape `/metrics` on a web instance — the process is down, wedged or unreachable.
- `ReadinessFailing`: the instance runs, but its last `/health/ready` check could not reach PostgreSQL, so the load balancer should have taken it out.
- `SiteProbeFailing`: the public `https://<domain>/health/ready`, probed from the host through DNS, TLS and Nginx, does not answer 200, while web itself is up (Alertmanager suppresses it when `WebDown` or `ReadinessFailing` fires). The problem sits between the user and the app: Nginx, the certificate, DNS or the firewall.
- Dead-man's switch paging: Prometheus or Alertmanager itself is down. Treat it as an outage until an external check proves the site is up.

## Check first

1. Is the site reachable from outside (browser, `curl -I https://<domain>/health/live`)? If not, look at DNS, TLS and Nginx before the app.
2. Container status and restarts for `web`. Was there a deploy in the last 30 minutes?
3. `curl -s -H "Authorization: Bearer $HEALTH_CHECK_TOKEN" https://<domain>/health/ready` — which check is down?
4. Disk space on the host (a full disk stops PostgreSQL and the logs).

## Mitigate

- PostgreSQL down or refusing connections → [R-5](./R-5.md).
- The failure started with a release → roll back.
- Container wedged (live but not answering) → restart it.
- Nginx/TLS problem → fix the config and reload.
- Monitoring stack down → `deploy/monitoring.sh ps`, then `deploy/monitoring.sh up -d`; until it is back, check the site by hand every 15 minutes.

## Escalate

No recovery in 15 minutes → communications.

## Resolved when

`up{job="web"} == 1` and `dependency_up{dependency="postgres"} == 1` for every instance, and the Watchdog reaches the dead-man's switch again.
