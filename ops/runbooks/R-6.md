# R-6 — Redis

**Alerts:** `QueueRedisDown`, `QueueRedisMemoryHigh` (page) · `CacheRedisDown` (ticket).

## What it means

There are two Redis servers:

- **Cache Redis** (`allkeys-lru`): rate limiting, unread counters, real-time hints. Losing it degrades features (the rate limiter falls back, clients refetch) but loses nothing durable.
- **Queue Redis** (`noeviction`, AOF): BullMQ jobs. While it is down no job is queued or run; the outbox holds the events, so nothing is lost. At 100 % memory every enqueue fails.

## Check first

1. Which instance? `redis-cli -u <url> ping`.
2. Memory: `redis-cli -u <url> info memory` (`used_memory`, `maxmemory`); evictions in `info stats`.
3. Queue Redis: AOF status in `info persistence`; failed-set size per queue (**Grafana → Async**, "Failed jobs retained").

## Mitigate

- Cache Redis down → restart it. Nothing to restore.
- Queue Redis down → restart it; the relay republishes from the outbox once it is back ([R-3](./R-3.md)).
- Queue Redis memory → find what fills it: a large failed set (retry or clear deliberately, [R-4](./R-4.md)), unexpectedly large payloads. Increase `maxmemory` if needed. **Never `FLUSHALL` the queue Redis.**

## Escalate

Queue data lost (AOF corrupted, volume gone) →.

## Resolved when

`redis_up == 1` for both and queue Redis memory under 70 %.
