# R-10 — Suspected compromise or data exposure

**Trigger:** no alert of its own. It starts from an anomaly another runbook escalates (R-9: a successful takeover, admin-tier denials from a real admin's account), a report from a member or researcher, or a notice from a provider (hosting, email, backup bucket, registrar).

Treat it as **SEV-1 until it is scoped**. One incident commander; a scribe keeps a timeline with UTC timestamps from the first minute. Reliability §10.6 is the source of this sequence.

## 1. Contain

Stop the exposure first, before investigating.

- **A feature or route leaks data:** turn it off at Nginx: `location … { return 503; }`, then `nginx -s reload`. The app has no feature kill switches; a rollback (reliability §8.5) also works if a release introduced the leak.
- **A source is attacking:** block its ranges at Nginx or ufw.
- **An account is compromised:** suspend it (admin → users) and end its sessions. Sessions are rows in `session`, and the cookie cache is off (ADR-005), so deleting them takes effect on the next request:
  ```bash
  docker compose exec postgres psql -U alumini -d alumini \
    -c "DELETE FROM session WHERE user_id = '<user id>';"
  ```
- **Every session must go** (a stolen `BETTER_AUTH_SECRET`): rotating the secret (step 4) invalidates every cookie.

## 2. Preserve

Do not wipe, rebuild or "clean" the host before the evidence is copied.

- Logs: `docker compose logs --timestamps > incident-<date>/compose.log`, and copy Nginx's access and error logs and `journalctl` for the window.
- A read-only database copy: `./backup.sh backup full` (it records the label), or `pg_dump` to a file off the host.
- Write down the times of everything you change from here on.

## 3. Scope

Answer: which data classes, which members, what time window.

- **Audit log** (admin → audit, or the `audit_log` table): privileged reads, role changes and decisions, each with `request_id`.
- **Logs** by `request_id` and `user_id`: the request path through web, outbox and worker.
- **Nginx access logs** for the source addresses and the routes they reached.
- **Grafana → Auth & security:** sign-ins by outcome and denials over the window.

## 4. Eradicate

- Fix the vulnerability, or keep the feature off until the fix ships through the normal release path (`deploy.sh promote`). An emergency fix still goes through staging.
- If the host itself may be compromised, rebuild it clean (reliability §7.1 scenario I): new server, deploy README from step 1, restore from a backup taken before the compromise.
- Rotate **every** secret in `deploy/.env` and `deploy/monitoring.env`:
  - `BETTER_AUTH_SECRET` (signs everyone out)
  - `POSTGRES_PASSWORD` (change it inside Postgres too, README "Secrets rotation")
  - `APP_DB_PASSWORD` (run the migrate job, then `up`)
  - `MINIO_ROOT_*`, `HEALTH_CHECK_TOKEN` and `SMTP_*`
  - the backup bucket key (`BACKUP_S3_KEY*`); review whether `BACKUP_CIPHER_PASS` was exposed
  - the receiver URLs in `monitoring.env`
  - the Server Actions key: a rebuild and a release replace it

## 5. Recover

- If data integrity is in doubt, restore to a point before the compromise (deploy README step 8, `backup.sh restore`; R-8).
- Force password resets for accounts whose credentials may be exposed: delete their sessions and send the reset link.
- Turn the feature back on once the fix is live, and watch R-9's signals for a day.

## 6. Notify

**The institute liaison decides** what members are told and what is reported to authorities, using the duties confirmed before launch (owner checklist OW-9, decision O-9):

- CERT-In's 2022 directions set a short reporting deadline for cyber incidents.
- The IT Act and the DPDP Act 2023 also apply.

Use the _Security notice_ template in `docs/operations/comms-templates.md`. Say what happened, what data was involved, what members should do and when the next update comes. Do not speculate.

## 7. Review

Hold a postmortem within 5 working days (`docs/incidents/YYYY-MM-DD-<slug>.md`, reliability §10.7). It includes a security review of the **class** of flaw, not only this instance: where else could the same mistake be?
