# R-4 — Dead jobs (dead-letter queue)

**Alerts:** `CriticalJobDead` (page: `donation.*`, `verification.*`) · `DeadJobsGrowing` (ticket: > 10 per hour).

## What it means

A job exhausted its retries or failed permanently and now sits in BullMQ's failed set (kept 7 days). Donation and verification jobs carry money or access decisions, so one is enough to page.

## Check first

1. `pnpm worker:cli jobs:list --queue <queue>` — job name, attempts and the failure reason (payloads are never shown: they hold personal data).
2. Error tracker: the dead job is reported with tags `queue`, `job`, `job_id` and the `request_id` of the request that produced it.
3. Logs: `event="job.dead"` with the same `jobId`; search the `request_id` to see the originating request.
4. For a provider failure (email), check the provider's status → [R-11](./R-11.md).

## Mitigate

1. Fix the cause first. Retrying a job that will fail the same way only adds noise.
2. Replay deliberately: `pnpm worker:cli jobs:retry --queue <queue> <id>...` (or `--all`). Processors are idempotent, so a retry does not duplicate work.
3. Donations: after replaying, check the campaign's admin screen for the expected state.
4. Notification emails: prefer the admin replay screen ([R-15](./R-15.md)), which is audited.

## Escalate

Suspected duplicate or lost payment → finance liaison.

## Resolved when

The failed set no longer grows and the replayed jobs completed.
